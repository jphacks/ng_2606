# 机の上ステージ：手順書の使い方マニュアル（メンバー向け）

このマニュアルは、A〜D の4人が Claude Code と一緒に、手順書（Docs/ClaudeCode/ の md）に沿って開発を進めるための説明書です。人が読むためのものです。Claude Code への指示は、CLAUDE.md と 00_overview.md、各担当の手順書に書いてあります。

## 1. 手順書セットの中身

| ファイル | 読む人 | 中身 |
| --- | --- | --- |
| CLAUDE.md（プロジェクトの一番上） | Claude Code | 起動したときに自動で読む入口。どの手順書を読むか、守るルールの要点 |
| Docs/ClaudeCode/00_overview.md | Claude Code と全員 | 全体のルール、共通コードの仕様、座標、全員でやる全体 Step 1〜4、品質目標、未決事項 |
| Docs/ClaudeCode/A_ar.md | A | AR・空間認識（面の検出、机の座標、もういちどスキャン、ビルド） |
| Docs/ClaudeCode/B_scan_data.md | B | 上面から箱を作る、補助、保存と読み込み、テストのまとめ |
| Docs/ClaudeCode/C_gameplay.md | C | キャラ、視点、ゲームの進行、スタートとゴール、高さの決まり |
| Docs/ClaudeCode/D_ui.md | D | 全画面、見た目、子どもテスト |
| Docs/ClaudeCode/MANUAL.md（このファイル） | 全員 | 進め方、進捗の管理、受け渡し表 |

各担当の手順書は、どれも同じ形をしています。

- 「進み具合」：全 Step のチェック欄。☐ はまだ、☑ は終わり
- 「作る部品の一覧」
- Step ごとの「目的」「やること」「確認」
- 「困ったとき」の表

Step の印の意味は次のとおりです。

| 印 | 意味 |
| --- | --- |
| 【CC】 | Claude Code がコードやファイルを作る |
| 【人】 | 人だけの作業（Unity エディタの操作、実機、物を測る、子どもテストなど）。Claude Code はやり方を説明して待つ |
| 【CC＋人】 | Claude Code が作り、人が Unity や実機で確かめる |

## 2. 全体の流れ

| フェーズ | ゴール | 全員で確かめること |
| --- | --- | --- |
| 準備 | A がプロジェクトと共通コードを作り、全員が受け取る | 全員の PC でプロジェクトが開く |
| P0 | 平らな面の検出を実機で検証する | 判定会議で案A〜D を決める |
| M1 | 並べた物をスキャンすると箱が生える | 実機で箱が生える |
| M2 | 箱づくりの完成、補助、保存と読み込み、ならべかたのコツ | 子どもテスト1回目 |
| M3 | 4人の部品を合流し、通して遊べる | 並べる→スキャン→たしかめる→保存→遊ぶ→並べ直す |
| M4 | ルール、エラー処理、照明のテスト | 子どもテスト2回目と時間の計測 |
| M5 | 見た目、文言、音、完成ビルド | 子どもテスト3回目と品質目標の最終確認 |

4人は自分の手順書を同時に進めます。他の人の部品がまだないときは、仮のもの（お手本ステージ、仮のボタン、PC の XR Simulation）で試せるように手順書を作ってあります。

## 3. 最初の準備

### 3.1 A がやること（全員の土台）

1. 00_overview.md の「全体 Step 1」を見ながら、Unity Hub とエディタで手作業でプロジェクトを作る
2. 配布された zip をプロジェクトの一番上で解凍する。CLAUDE.md と Docs/ が Assets/ と同じ階層に来るようにする
3. VS Code でプロジェクトのフォルダを開き、Claude Code に「00_overview.md の全体 Step 2 を進めて」と頼む（Git と GitHub の準備）
4. 続けて「全体 Step 3 を進めて」と頼む（共通コード）
5. 共通コードを全員に見せて了承をもらい、main に入れる
6. チャットで「準備完了。clone できます」と知らせる

### 3.2 B・C・D がやること（各自1回だけ）

インストールは Claude Code にはできません。自分で行います。

| やること | 済 |
| --- | --- |
| GitHub のアカウントを作り、A からの招待を受ける | ☐ |
| Git と Git LFS をインストールする | ☐ |
| Unity Hub と、A と同じバージョンの Unity 6 をインストールする（iOS Build Support は Mac を使う人だけ） | ☐ |
| VS Code をインストールし、拡張機能「Claude Code」を入れてログインする | ☐ |
| VS Code に Microsoft の「Unity」拡張機能を入れ、Unity の Preferences → External Tools でエディタを VS Code にする | ☐ |
| A の「準備完了」の後、リポジトリを clone し、Unity Hub で開く（エラーなく開けば OK） | ☐ |
| VS Code で、clone したフォルダ（CLAUDE.md がある一番上）を開く | ☐ |

Git が入っていれば、clone は Claude Code に頼めます。clone した後は、そのフォルダを VS Code で開き直してください。

## 4. 毎回の進め方（1 Step のサイクル）

1 Step ごとに、次の8つをくり返します。

| 順番 | 誰が | すること |
| --- | --- | --- |
| 1 | 人 | Claude Code のパネルで新しい会話を始める |
| 2 | 人 | 「main を最新にして、自分の担当の英字/内容 のブランチを作って」と頼む（例：b/box-builder） |
| 3 | 人 | 「私は B 担当です。B_scan_data.md の次の Step を進めて」と頼む |
| 4 | Claude Code | 手順書を読み、最初の ☐ の Step を作業する。【人】の作業があれば、やり方を説明して止まる |
| 5 | 人 | Unity に切り替えて確かめる（5章） |
| 6 | 人 | うまくいけば「確認できた。次へ」。だめなら Unity の Console のエラー文や画面の写真を渡す |
| 7 | Claude Code | 手順書の ☐ を ☑ にしてコミットする |
| 8 | 人 | GitHub でプルリクエストを作り、チャットで知らせる（6章） |

コツ：

- 1つの会話で1 Step だけ進める。Step が終わったら新しい会話にする。進み具合は手順書の ☑ に残るので、続きから再開できる
- Claude Code がファイルを変える前に許可を求める設定のまま使う。何を変えるかを見てから許可する
- Step が大きすぎると感じたら「この Step を小さく分けて、1つ目だけやって」と頼む

## 5. Unity での確かめ方（人の作業）

Claude Code は Unity の画面を見られません。確かめるのは人の役目です。

| Claude Code に言われること | Unity でやること |
| --- | --- |
| 「メニューを実行してください」 | 上のメニューの DeskStage → 自分の担当 → 指定の項目を押す。シーンやプレハブはこの方法で作る |
| 「テストを流してください」 | Window → General → Test Runner → EditMode → Run All。全部が緑なら OK。赤があれば、その名前とメッセージを伝える |
| 「再生して確かめてください」 | 指定のテスト用シーン（Test_A〜Test_D）を開いて再生し、言われたことを見る |
| 「実機で確かめてください」 | Mac で iPhone にビルドする。Mac を使う日は事前にチャットで決める |

エラーが出たとき：

- Window → General → Console を開き、赤い行を選ぶと下に全文が出る。それを全部コピーして Claude Code に貼る
- Unity に切り替えたときに自動でコンパイルされる。コンパイルエラーがあると再生できないので、まずそれを直してもらう
- Claude Code が「2回直しても通らない」と言って止まったら、無理に続けず、チームのチャットで相談する

## 6. Git とプルリクエスト

| 決まり | 内容 |
| --- | --- |
| ブランチ | 担当の英字/内容（例：a/plane-watcher、c/game-flow）。main で直接作業しない |
| コミット | Claude Code がこまめに行う。説明は日本語で1行 |
| プルリクエスト | Step が終わり確認が済んだら、人が作る。「何を作ったか・どう確かめたか・画面の写真か動画」を書く |
| 承認 | 担当以外の1人が見て承認したら、main に合流する |
| Main.unity | 合流（M3）以降、触る前に「Main触ります」、終わったら「Main終わりました」とチャットで言う |

プルリクエストの説明文は、Claude Code に「このブランチのプルリクエストの説明を書いて」と頼むと下書きを作ってくれます。

## 7. 進捗の管理

### 7.1 進捗はどこにあるか

- 各担当の手順書の「進み具合」の ☑ が、そのまま進捗表になる
- ☑ が main に見えるのは、プルリクエストが合流した後。作業中の様子は本人のブランチにしかない
- そのため、☑ とチャットの一言を合わせて使う

### 7.2 確かめ方

| 知りたいこと | 方法 |
| --- | --- |
| 全員の進み具合 | Claude Code に「main を最新にして、A〜D の手順書の進み具合をまとめて」 |
| 自分が待っている物ができたか | Claude Code に「MANUAL.md の受け渡し表で、私（B）が待っている物はできた？」 |
| まだ main に入っていない作業 | GitHub の Pull requests の一覧を見る |

### 7.3 チャットで知らせる決まり

| とき | 書き方の例 |
| --- | --- |
| Step が終わって main に入れた | 「A：Step 11（面の安定化）main に入れました。B さん箱づくりを実機で試せます」 |
| 遅れそう | 「A：Step 11 が来週にずれそうです。B さんは Step 10 を先に進めてください」 |
| 誰かに頼みたい | 「B→D：一覧の渡し方を決めたいです。今日か明日に10分話せますか」 |
| 実機を使いたい | 「Mac と iPhone を水曜の放課後に使いたいです」 |
| 共通コードを変えたい | 「C：共通コードに○○を足したいです。案を GitHub に置きました。全員の確認をお願いします」 |

### 7.4 週1回の進捗会（10分）

1. 誰か1人が Claude Code に全員の進み具合をまとめてもらい、画面で見せる
2. 8章の受け渡し表で、「誰が何を待っているか」「いつ渡せそうか」を確かめる
3. 来週 Mac を使う日、【未決】で決めることを決める
4. A がその週の main を実機ビルドして全員の iPhone に入れる（無料の Apple ID のアプリは7日で開けなくなる）

## 9. 待つときにやること

待っている間も、手を止めずに進められる作業があります。

| 担当 | 待っている物 | その間にやること |
| --- | --- | --- |
| 全員 | 共通コード | 自分の手順書を読む。B は物をそろえて測る |
| B | A の上面 | テストだけで Step 6・7 の計算を仕上げる。Step 10・11 を先に進める |
| C | B のステージ | 練習用シーン（Test_C）でキャラと視点を作り込む |
| D | A・B・C の出来事 | 仮のボタンで画面の流れを作る。文言の表と素材を進める |
| A | 実機の日 | PC の XR Simulation とテストでできる所を済ませる |

Claude Code には「○○の部品がまだないので、仮のもので試せるようにして」と頼めます。ただし、仮のものは開発用の印を付け、合流の前に消します。

## 10. Claude Code への頼み方の例

| 場面 | 頼み方 |
| --- | --- |
| 次の Step を始める | 「私は C 担当です。C_gameplay.md の次の Step を進めて」 |
| 今どこにいるか知りたい | 「D_ui.md の進み具合を見て、次の Step の中身を短く教えて」 |
| Step が大きい | 「この Step を小さく分けて、1つ目だけやって」 |
| エラーが出た | 「Unity でこのエラーが出た：（エラー文を全部貼る）」 |
| テストが赤い | 「Test Runner でこのテストが失敗した：（名前とメッセージ）」 |
| 他の部品を待っている | 「A の部品がまだないので、仮のもので試せるようにして」 |
| 手順書と違うことをしたい | 「手順書の○○を△△に変えたい。影響する所を教えて。まだ変えないで」 |
| 作った物の説明がほしい | 「今の Step で作った物を、仕組みが分かるように説明して」 |

## 11. Claude Code が止まって聞いてきたとき

Claude Code は、次のときに作業を止めて人に聞くように手順書で決めてあります。勝手に答えを決めず、下の表のとおりに対応してください。

| 止まった理由 | 人がすること |
| --- | --- |
| 【人】の Step | 説明されたとおりに作業し、終わったら結果を伝える |
| 【未決】の項目 | 仮の決め方で進めてよいかをチームで決める。決まったら 00_overview.md の8章を直す |
| 共通コードを変えたい | 案を全員に見せて合意を取る。合意の後、A がまとめて変える |
| 手順書に書いていない・食い違う | チャットで相談し、決まったことを手順書に書き足す |
| 新しいパッケージを入れたい | 全員に相談する。入れるなら全員の Unity にも入る |
| 2回直しても確認が通らない | 一度止めて、チャットで相談する。同じ担当の経験者や、関係する担当に見てもらう |

## 12. 手順書を直すとき

- 手順書も Git で管理する。直すときもブランチとプルリクエストで行う
- 自分の担当の手順書は、自分で直してよい（Step を分ける、数値を変える）。関係する担当に知らせる
- 00_overview.md と共通コードの仕様（4章）は、全員の合意の後に A が直す
- 数値を変えたとき（ジャンプの高さなど）は、関係するすべての手順書と Docs のファイルを直す。Claude Code に「○○を変えた。影響する手順書と Docs を全部探して直す案を出して」と頼むと漏れにくい

## 13. やってはいけないこと

- main で直接作業する
- .unity、.prefab、.meta のファイルを手やテキストで書き換える（Unity のメニューで作る）
- 他の担当のフォルダのファイルを変える
- 共通コードを合意なしに変える
- 確かめずに ☑ を付ける
- Claude Code が止まったときに、内容を読まずに「いいよ」と答える
- Main.unity を宣言なしで触る
